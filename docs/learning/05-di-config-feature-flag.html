Mục 1Sau bài này bạn làm được gì

  • Chọn đúng chỗ đặt một provider, và nói được nó cho tuổi thọ nào.
  • Viết một InjectionToken cho thứ không phải class — ví dụ một khả năng của trình duyệt — sao cho code gọi không phải kiểm tra if (isBrowser).

Mục 3Cơ chế

3.1 inject() và injection context

khuôn gặp ở mọi nơi trong repo
@Injectable({ providedIn: 'root' })
export class CustomerApi {
  private readonly http = inject(HttpClient);          // field initializer: OK
  private readonly config = inject(AppConfigStore).config;
}

inject() hợp lệ ở bốn chỗ, và chỉ bốn chỗ: field initializer, thân constructor, factory của một provider, và một hàm được gọi từ những chỗ đó (lockScrollWhile ở bài 03 là ví dụ loại cuối).

Gọi sai chỗ thì lỗi lúc chạy, không phải lúc biên dịch 
protected onSave(): void {
  const logger = inject(Logger);   // NG0203: inject() must be called from an
                                   // injection context
}

Cách đúng: inject ở field, dùng ở method. Nếu thật sự cần inject muộn — hiếm — thì giữ một Injector rồi runInInjectionContext(injector, () => …). customer-list-page.ts giữ một Injector đúng vì lý do họ hàng: truyền nó cho afterNextRender gọi từ trong một effect.

3.2 Cây injector: chỗ đặt provider quyết định tuổi thọ

Quy tắc tra cứu: Angular đi từ injector gần nhất lên dần tới gốc, lấy cái đầu tiên biết trả lời.

Khai ở đâu Bao nhiêu instance Chết khi nào Dùng cho
providedIn: 'root' Một, cho cả app Đóng tab Hạ tầng và state toàn cục: SessionService, AppConfigStore, ThemeService, CustomerApi
providers trên route Một, cho cả nhánh route Rời khỏi nhánh State của một feature: CustomerStore, CustomerCache
providers trên component Một cho mỗi lần dựng Component bị huỷ Hiếm. Khi state thuộc đúng một màn hình cụ thể
Vì sao CustomerApi ở 'root' mà CustomerStore thì không

CustomerApi không giữ state — nó chỉ biến request thành giá trị. Một instance dùng chung không hại gì. CustomerStore giữ cache và lịch sử duyệt của một người; để nó ở 'root' nghĩa là cache sống qua cả một lần đăng xuất. Đó là lập luận trong chú thích đầu customers.routes.ts, và nó là một trong những quyết định đáng mang đi nhất của repo.

3.3 Token cho thứ không phải class

Bạn không inject(window) được — window không phải class, và trên server nó không tồn tại. Đây là lúc cần InjectionToken:

core/platform/platform.tokens.ts
export const IS_BROWSER = new InjectionToken<boolean>('ecm.isBrowser', {
  providedIn: 'root',
  factory: () => isPlatformBrowser(inject(PLATFORM_ID)),
});

export const WINDOW = new InjectionToken<Window | null>('ecm.window', {
  providedIn: 'root',
  factory: () => inject(DOCUMENT).defaultView,
});
Thành phần Nghĩa
new InjectionToken<Window | null>(…) Tạo một khoá có kiểu. Generic là thứ làm inject(WINDOW) trả về đúng kiểu Window | null.
'ecm.window' Mô tả, chỉ hiện trong thông báo lỗi. Tiền tố để không trùng với token của thư viện khác.
providedIn: 'root' + factory Token tự khai luôn cách tạo ra mình. Nhờ vậy không file nào khác phải nhớ đăng ký nó — và nếu không ai xin thì nó không bao giờ được tạo.
inject(DOCUMENT).defaultView Lấy window qua document mà Angular cung cấp, nên trên server nó là null một cách tự nhiên thay vì ném lỗi.

Thiết kế đáng học: thu hẹp API thay vì bọc nguyên

cùng file
/**
 * The subset of `Storage` the application is allowed to use.
 *
 * Deliberately not the DOM `Storage` interface: `key()`, `length` and `clear()`
 * invite code that walks or wipes storage owned by someone else.
 */
export interface KeyValueStorage {
  read(key: string): string | null;
  write(key: string, value: string): void;
  remove(key: string): void;
}

Ba phương thức, không phải cả Storage. Lý do viết thẳng trong chú thích: clear() xoá cả storage của thứ khác trên cùng origin, và key()/length mời gọi code đi duyệt storage của người khác. Một seam không chỉ để thay thế được — nó còn là chỗ thu hẹp quyền.

Và phần làm cho code gọi không phải phân nhánh:

cùng file
class UnavailableStorage implements KeyValueStorage {
  read(): string | null {
    return null;
  }
  write(): void {
    /* intentionally empty */
  }
  remove(): void {
    /* intentionally empty */
  }
}

function storageFrom(pick: (win: Window) => Storage): KeyValueStorage {
  const win = inject(WINDOW);
  if (!win) {
    return new UnavailableStorage();
  }
  try {
    // Touching the property can throw before we ever read a key.
    return new WebStorage(pick(win));
  } catch {
    return new UnavailableStorage();
  }
}

Trên server, trong cửa sổ ẩn danh, khi người dùng chặn site data — LOCAL_STORAGE vẫn trả về một đối tượng dùng được, chỉ là nó không làm gì. Mẫu này có tên: null object. Nhìn lại ThemeService ở bài 03: nó gọi this.storage.read(STORAGE_KEY) thẳng, không một dòng kiểm tra môi trường nào.

3.4 Bốn cách trả lời một token

Cách Ví dụ thật trong repo Nghĩa
useClass { provide: TitleStrategy, useClass: TranslatedTitleStrategy } Xin cái của Angular, nhận bản của repo. Đây là cách thay một mảnh của framework mà không fork nó.
useClass { provide: ErrorHandler, useClass: GlobalErrorHandler } Mọi lỗi chưa bắt được đi qua lớp của repo.
useExisting { provide: HttpBackend, useExisting: UploadAwareBackend } Cùng một instance trả lời hai token. useClass ở đây sẽ tạo ra hai đối tượng, và trạng thái của chúng sẽ lệch.
useValue Trong các file test, để đưa vào một bản giả Trả thẳng một giá trị có sẵn.
factory Mọi token trong platform.tokens.ts Gọi một hàm để tạo — hàm đó lại được phép inject().

3.5 Khuôn provideX()

core/core.providers.ts
export function provideCore(): EnvironmentProviders {
  return makeEnvironmentProviders([
    provideObservability(),
    { provide: ErrorHandler, useClass: GlobalErrorHandler },
    provideAppHttp(),
    provideI18n(),
    // After provideI18n(): it subscribes to the translation service.
    provideDocumentLanguage(),
    provideRuntimeConfig(),
    // Needs the router, which app.config provides alongside this; environment
    // initializers run once the whole injector exists.
    provideSessionExpiryRedirect(),
    provideSessionCrossTab(),
  ]);
}

Khuôn này là cách Angular hiện đại gói hạ tầng, và nó thay cho NgModule của thời trước. Ba điều nó mua được:

  • Một tên cho một nhóm. app.config.ts đọc ra là danh sách những thứ ứng dụng là, không phải một đống provider không ai dám sắp xếp lại.
  • Chỗ để viết ràng buộc thứ tự. Hai chú thích trong đoạn trên là hai ràng buộc thật, và chúng nằm ngay cạnh code chúng ràng buộc.
  • Thêm hạ tầng không phải sửa file bootstrap.

3.6 provideAppInitializer: cấu hình trước khi render

core/config/runtime-config.provider.ts — rút gọn
export function provideRuntimeConfig(): EnvironmentProviders {
  return makeEnvironmentProviders([
    provideAppInitializer(async () => {
      if (!inject(IS_BROWSER)) {
        return;
      }

      const http = inject(HttpClient);
      const store = inject(AppConfigStore);
      const logger = inject(Logger);
      const language = inject(LanguageService);

      let raw: unknown;
      try {
        raw = await firstValueFrom(http.get<unknown>(RUNTIME_CONFIG_URL));
      } catch {
        logger.warn('Runtime configuration unavailable; using defaults', { … });
      }

      if (raw !== undefined) {
        const parsed = appConfigOverridesSchema.safeParse(raw);
        if (parsed.success) {
          store.apply(parsed.data);
        } else {
          logger.error('Runtime configuration invalid; using defaults', { … });
        }
      }

      await language.restore(store.config().defaultLanguage);
    }),
  ]);
}
Quyết định Lý do
Trả về sớm nếu không phải trình duyệt Server fetch file tĩnh của chính nó là gửi một request cho chính mình. Bản render phía server dùng mặc định biên dịch sẵn, và trình duyệt cấu hình lại khi hydrate.
Fetch hỏng thì warn rồi chạy tiếp "Khởi động với mặc định tốt hơn là không khởi động." Nhưng phải có cảnh báo, nếu không một file thiếu sẽ thành một lỗi bí ẩn ba tháng sau.
Cấu hình sai thì bỏ hết, không áp một phần Chú thích nói rõ: "nửa cấu hình — URL áp mà flag không — là một trạng thái chưa ai test. Mặc định thì có."
Chọn ngôn ngữ ở trong initializer này Các initializer khởi động cùng lúc. Một initializer riêng cho ngôn ngữ sẽ đọc mặc định trước khi cái này kịp thay. Thứ tự là lý do nó nằm chung chỗ, và await là lý do lần render đầu đã đúng ngôn ngữ.

3.7 Cấu hình: build-time và runtime

core/config/app-config.ts
export interface AppConfig {
  readonly apiBaseUrl: string;
  readonly defaultLanguage: string;
  readonly logLevel: LogLevel;
  readonly features: Readonly<Record<FeatureFlag, boolean>>;
}

export const DEFAULT_APP_CONFIG: AppConfig = {
  apiBaseUrl: '/api',
  defaultLanguage: 'en',
  logLevel: 'info',
  features: { technicalLabs: true, routePreloading: true, customerImport: true },
};

Nguyên tắc ở đầu file: "One built artifact is promoted from staging to production unchanged; what differs between them is fetched from /config.json at boot." Và ngay sau đó: "Nothing secret goes here. This file is served to every browser."

Vì sao file cấu hình phải được validate

cùng file
export const appConfigOverridesSchema = z.strictObject({
  apiBaseUrl: z
    .string()
    .regex(SAME_ORIGIN_PATH, 'must be a same-origin path such as "/api"')
    .optional(),
  defaultLanguage: z.string().min(2).max(10).optional(),
  logLevel: z.enum(LOG_LEVELS as [LogLevel, ...LogLevel[]]).optional(),
  features: z.strictObject({ … }).optional(),
});

Ba lý do, cả ba đều rút từ chuyện đã xảy ra thật:

  • File do người sửa tay, theo từng môi trường, bởi người không đọc code này. "technicalLabs": "false" là một chuỗi, và chuỗi thì truthy — flag sẽ không bao giờ tắt.
  • strictObject, nên khoá viết sai là lỗi tự nói tên nó. "customerImprot" mà im lặng thì bạn sẽ đi tìm bug ở chỗ khác.
  • apiBaseUrl phải là đường dẫn cùng origin. Chú thích ghi lại một sự cố thật: một URL tuyệt đối đã qua được kiểm tra và làm mọi lệnh ghi bị 403, vì cookie phiên là first-party và csrfInterceptor chỉ đóng dấu lên URL tương đối.

3.8 Feature flag: hai loại, và lý do kỹ thuật để phân biệt

core/config/feature-flags.ts
@Injectable({ providedIn: 'root' })
export class FeatureFlags {
  private readonly config = inject(AppConfigStore).config;

  isEnabled(flag: FeatureFlag): boolean {
    return this.config().features[flag];
  }
}

Bốn dòng, nhưng chú thích của nó dài gấp năm lần, và đoạn quan trọng nhất là đoạn giải thích vì sao build-time flag cố ý không đọc được ở đây:

Vì sao build-time flag phải đọc như hằng số

Một build-time flag tồn tại để code không được lên production. Điều đó chỉ xảy ra nếu bundler nhìn thấy nhánh đó là chết và xoá đi. Viết if (environment.buildFlags.enableDevTools) thì nó thấy. Viết if (this.flags.isEnabled('devTools')) thì nó không thể biết giá trị, nên nó giữ lại cả nhánh — và code bạn muốn loại bỏ vẫn nằm trong bundle gửi tới người dùng. Đó là đúng một tính chất mà build-time flag tồn tại vì nó.

Runtime flag Build-time flag
Đọc ở đâu FeatureFlags.isEnabled() Hằng số trong environments/
Đổi được bằng cách Sửa config.json, nạp lại trang Build lại
Code có trong bundle không Có Không — đó là lý do tồn tại
Dùng cho Một quyết định: môi trường này có mở nhập liệu hàng loạt không Code không được ship: công cụ cho lập trình viên

Flag áp vào route: cả nhánh biến mất

app/app.routes.ts và customers/customers.routes.ts
{
  path: 'technical-labs',
  // A disabled flag makes the branch stop matching, so the request falls
  // through to the wildcard below and the chunk is never loaded.
  canMatch: [featureEnabled('technicalLabs')],
  loadChildren: () => import('./technical-labs/technical-labs.routes')…,
},

{
  path: 'import',
  canMatch: [featureEnabled('customerImport')],
  …
}

canMatch chứ không phải canActivate, và khác biệt quan trọng: canActivate nói "route này tồn tại nhưng bạn không được vào" — nó đã nạp chunk rồi mới từ chối. canMatch nói "route này không khớp", nên router đi tiếp xuống wildcard và chunk không bao giờ được tải. Với một tính năng bị tắt, đó là hành vi đúng cả về trải nghiệm lẫn về dung lượng tải.

5.1 Cấu hình đi từ file tới màn hình

Mục 6Đánh đổi & phương án bị loại

Cấu hình runtime thay vì biên dịch vào bundle — ADR-0005

Phương án bị loại: environment.prod.ts với URL API ghi cứng, build riêng cho từng môi trường. Bị loại vì khi đó thứ chạy ở production không phải thứ đã test ở staging — nó là một bản build khác. Giá phải trả: một request nữa lúc khởi động, và một file phải nhớ đặt đúng chỗ khi deploy.

KeyValueStorage thay vì Storage

Phương án bị loại: cung cấp thẳng Storage của DOM. Bị loại vì nó kèm clear() và key() — những hàm mời gọi code đụng vào dữ liệu của thứ khác trên cùng origin. Giá phải trả: ba phương thức phải tự viết, và hai lớp cài đặt.

Không dùng một nền tảng feature flag

Phương án bị loại: LaunchDarkly, Unleash, hoặc một endpoint riêng. Chú thích ghi rõ repo cố ý không có targeting, không phần trăm, không đánh giá từ xa — và nói luôn điều kiện để đổi ý: khi một flag cần một trong những thứ đó, class này trở thành adapter cho dịch vụ kia.

Một flag không có kế hoạch gỡ thì không phải flag

Luật trong app-config.ts: thêm một flag thì phải thêm một dòng trong docs/feature-flags.md kèm chủ sở hữu và điều kiện gỡ bỏ. "Một flag không ai định gỡ là cấu hình, và nó thuộc về AppConfig dưới dạng một thiết lập có tên."

Mục 7Làm kiểu ngây thơ thì vỡ thế nào

1. inject() trong một method

NG0203: inject() must be called from an injection context. Lỗi lúc chạy, và thường chỉ xuất hiện khi người dùng bấm vào đúng nút đó. Inject ở field, dùng ở method.

2. Để state của feature ở providedIn: 'root'

Cache và lịch sử duyệt của một người sống bằng tuổi của tab — kể cả sau khi đăng xuất và người khác đăng nhập vào. Đây không chỉ là chuyện bộ nhớ.

3. useClass ở chỗ cần useExisting

{ provide: HttpBackend, useClass: UploadAwareBackend } tạo ra hai instance. Mọi state bên trong chúng lệch nhau, và triệu chứng thường là "lúc được lúc không" tuỳ ai gọi qua token nào.

4. Đọc build-time flag qua một service

Bundler không còn thấy nhánh chết, nên code lẽ ra không được ship vẫn nằm trong bundle. Flag vẫn "hoạt động" — tính năng vẫn tắt — nên không ai phát hiện, cho tới khi ai đó đọc bundle.

5. Tin config.json mà không validate

"customerImport": "false" là chuỗi, và chuỗi thì truthy — tính năng bạn vừa tắt vẫn bật. Khoá viết sai thì im lặng bị bỏ qua. Cả hai lỗi đều do người không đọc code này gây ra, ở một môi trường bạn không mở được.

Mục 8Test ở đâu, khẳng định điều gì

DI là thứ làm test khả thi: thay một provider là thay cả một tầng, mà không file nào trong ứng dụng phải biết.

File Khẳng định

Với mỗi trường hợp, ghi lại: ứng dụng có chạy không, và nó nói gì?

Bạn phải thấy gì, và bài học

Cả ba đều bị schema chặn, log error, và ứng dụng chạy bằng toàn bộ cấu hình mặc định. Đó là luật "tất cả hoặc không gì" ở mục 3.6.

Bây giờ hình dung nếu không có schema: trường hợp 1 làm tính năng bạn vừa tắt vẫn bật; trường hợp 2 im lặng hoàn toàn; trường hợp 3 làm mọi lệnh ghi trả 403 vì cookie first-party không đi theo và CSRF không được đóng dấu — đúng sự cố mà chú thích trong app-config.ts ghi lại.

Bài 3 — Viết một token cho một khả năng của trình duyệt

~45 phút · branch learning/*

Viết VIBRATION: một token cho navigator.vibrate, để code gọi rung được mà không bao giờ chạm vào global và không phải kiểm tra môi trường.

  • Đặt trong core/platform/platform.tokens.ts, theo đúng khuôn.
  • Thiết kế interface hẹp: chỉ thứ ứng dụng cần, không bọc cả API.
  • Trên server, và trong trình duyệt không hỗ trợ: trả về một bản null object. Code gọi không được có if nào.
  • Viết spec khẳng định cả hai trường hợp.
Ba câu để tự chấm
  1. Code gọi có dòng nào kiểm tra IS_BROWSER không? Có thì seam chưa đạt — so với ThemeService gọi storage.read() thẳng.
  2. Token của bạn có dùng inject(NAVIGATOR) trong factory không? Nên có — token dựng trên token khác là bình thường và đúng.
  3. Bạn có bọc cả Navigator không? Đừng. Đọc lại chú thích của NAVIGATOR: repo cố ý không bọc từng khả năng một, vì mỗi cái đã là một object có feature test riêng, và bọc thêm là một trừu tượng chỉ có một người gọi — rule 8 trong CLAUDE.md.

Bài 4 — Thêm một runtime feature flag, đầu đến cuối

~45 phút · branch learning/* · bài chính

Thêm flag customerExport: khi tắt, nút Export trên trang danh sách biến mất.

  1. Thêm vào FEATURE_FLAGS và vào DEFAULT_APP_CONFIG.
  2. Dùng nó trong customer-list-page.ts.
  3. Thêm một dòng vào docs/feature-flags.md kèm chủ sở hữu và điều kiện gỡ bỏ.
  4. Tắt nó trong config.json và xác nhận nút biến mất.
  5. npm run lint, npm run typecheck, npm test sạch.
Hai câu hỏi thiết kế, và một cái bẫy

Câu 1: runtime hay build-time? Runtime — đây là một quyết định theo môi trường, không phải code cần bị xoá khỏi bundle.

Câu 2: flag này đặt ở nút hay ở route? Nút, vì không có route riêng cho export. So sánh với customerImport: nó có route /customers/import, nên nó dùng canMatch để cả nhánh biến mất và ẩn nút. Hai lớp cho hai lý do khác nhau.

Cái bẫy: ẩn nút không phải là tắt tính năng. Người dùng vẫn gọi được endpoint export bằng curl. Nếu đây là một giới hạn thật thì mock API cũng phải từ chối. Quy tắc 10: frontend là UX, không phải biên bảo mật — và bài 20 nói đủ về chuyện này.

Mục 11Tự kiểm tra

1. inject() gọi được ở đâu?

Field initializer, thân constructor, factory của provider, và hàm được gọi từ những chỗ đó. Ngoài ra ném NG0203 lúc chạy. Cần inject muộn thì giữ một Injector và dùng runInInjectionContext.

2. Vì sao CustomerApi ở 'root' còn CustomerStore thì ở route?

CustomerApi không giữ state — một instance chung vô hại. CustomerStore giữ cache và lịch sử duyệt của một người; ở 'root' nó sẽ sống qua một lần đăng xuất.

3. Khi nào cần InjectionToken thay vì dùng chính class làm token?

Khi không có class nào để trỏ tới: một giá trị (IS_BROWSER), một đối tượng của trình duyệt (WINDOW, NAVIGATOR), một hàm factory (EVENT_SOURCE_FACTORY), hoặc một interface — interface biến mất sau khi biên dịch nên không làm token được.

4. useExisting khác useClass ở đâu, và khi nào sai lầm đó đau?

useExisting trỏ sang một instance đã có; useClass tạo một instance mới. Dùng useClass cho HttpBackend → hai backend tồn tại song song, state lệch, lỗi "lúc được lúc không".

5. Vì sao config.json phải validate bằng schema?

Vì nó do người sửa tay, theo môi trường, bởi người không đọc code. "false" là chuỗi truthy; khoá viết sai thì im lặng; apiBaseUrl tuyệt đối làm mọi lệnh ghi 403. strictObject biến cả ba thành lỗi tự nói tên nó.

6. Vì sao build-time flag không được đọc qua một service?

Vì bundler phải nhìn thấy nhánh là chết mới xoá được code đi. Đọc qua một lời gọi hàm thì nó không biết giá trị và giữ lại cả nhánh — mất đúng tính chất duy nhất mà build-time flag tồn tại vì nó.

7. canMatch khác canActivate thế nào với một flag?

canActivate: route tồn tại, chunk được tải, rồi mới từ chối. canMatch: route không khớp, router đi tiếp xuống wildcard, chunk không bao giờ được tải. Với một tính năng bị tắt, canMatch là đúng.

8. Khi nào một "flag" thật ra là cấu hình?

Khi không ai có kế hoạch gỡ nó. Luật trong repo: mỗi flag phải có chủ sở hữu và điều kiện gỡ bỏ ghi trong docs/feature-flags.md; không có thì nó thuộc về AppConfig dưới dạng một thiết lập có tên.

HttpClient + contract Zod

Gọi HTTP trong Angular mất năm phút để học. Bài này dành phần lớn thời gian cho câu hỏi khó hơn: làm sao biết thứ server trả về đúng là thứ bạn nghĩ? TypeScript không trả lời được câu đó — generic biến mất lúc chạy. Câu trả lời của repo là một gói contract dùng chung, và nó là thứ đáng mang đi nhất chặng này.

  • Chuyển được sang dự án thật
  • Chặng 2 · hướng tới Mốc 2
  • ~3 giờ đọc + 2 giờ làm

Mục 1Sau bài này bạn làm được gì

  • Viết một lời gọi API mới theo đúng khuôn của repo.
  • Giải thích được vì sao http.get<Customer>() là một lời hứa không ai kiểm, và cái gì thay thế nó.
  • Đọc một schema Zod và nói được nó cho phép gì, chặn gì.
  • Biết vì sao CustomerId và UserId không thay nhau được, dù cả hai là chuỗi.
  • Nói được một response 200 với body sai hợp đồng thì ai chịu trách nhiệm, và người dùng thấy gì.

Mục 3Cơ chế

3.1 HttpClient: những gì bạn cần

tổng hợp từ customer.api.ts
// GET có query param
this.http.get<unknown>(this.baseUrl, { params: toHttpParams(criteria) });

// GET một bản ghi
this.http.get<unknown>(`${this.baseUrl}/${encodeURIComponent(id)}`);

// POST
this.http.post<unknown>(this.baseUrl, input);

// PATCH
this.http.patch<unknown>(`${this.baseUrl}/${encodeURIComponent(id)}`, input);

// DELETE
this.http.delete<unknown>(`${this.baseUrl}/${encodeURIComponent(id)}`);

// Tải file, kèm tiến độ
this.http.get(`${this.baseUrl}/export`, {
  params: toHttpParams(criteria),
  observe: 'events',
  reportProgress: true,
  responseType: 'blob',
});
Chi tiết Nghĩa
encodeURIComponent(id) Id đi vào đường dẫn, nên phải tự encode. Một id chứa / mà không encode sẽ gọi nhầm endpoint.
{ params } Query string. HttpClient tự encode — không bao giờ tự nối chuỗi vào URL.
observe: 'events' Mặc định HttpClient chỉ phát body. 'events' phát cả tiến độ — cần cho upload và download lớn.
responseType: 'blob' Không parse JSON; trả về dữ liệu nhị phân.
Không có await Mọi hàm trả về Observable, chưa chạy. Bài 07.

HttpParams là bất biến

customers/data/customer.api.ts
function toHttpParams(criteria: CustomerListCriteria): HttpParams {
  let params = new HttpParams()
    .set('page', criteria.page)
    .set('size', criteria.size)
    .set('sort', criteria.sort);

  const optional: Record<string, string> = {
    search: criteria.search,
    status: criteria.status,
    // …
  };

  for (const [key, value] of Object.entries(optional)) {
    if (value) {
      params = params.set(key, value);
    }
  }

  return params;
}

Chú ý params = params.set(...): mỗi set trả về một đối tượng mới. Viết params.set(...) mà không gán lại là một lỗi im lặng — tham số đơn giản không xuất hiện.

Và một quyết định nhỏ đáng đọc: page và size luôn được gửi, kể cả khi trùng mặc định. Lý do trong chú thích: dựa vào mặc định của server nghĩa là client và server mỗi bên có ý kiến riêng về cỡ trang — và chúng sẽ đồng ý cho tới ngày một bên đổi.

3.2 Generic là lời hứa, không phải kiểm tra

hai dòng này biên dịch ra JavaScript giống hệt nhau
this.http.get<Customer>('/api/customers/1');
this.http.get<unknown>('/api/customers/1');

Generic bị xoá. Lúc chạy, HttpClient nhận JSON, gọi JSON.parse, và trả về bất cứ thứ gì có trong body. Nếu server trả thiếu email, TypeScript vẫn tin rằng customer.email là string, và lỗi sẽ nổ ở một template ba tầng sau với thông báo chẳng liên quan gì tới nguyên nhân.

Vì vậy repo khai <unknown> — nói thật rằng chưa biết gì — rồi dựng sự thật bằng một phép kiểm tra thật:

customers/data/customer.api.ts
function parseWith<S extends z.ZodType>(schema: S): (body: unknown) => z.output<S> {
  return (body) => {
    const parsed = schema.safeParse(body);
    if (!parsed.success) {
      throw appError('server', { messageKey: 'errors.server', cause: parsed.error });
    }
    return parsed.data;
  };
}

Sau parseWith, kiểu Customer không còn là lời hứa — nó là kết luận của một phép kiểm tra vừa chạy.

Một 200 sai hợp đồng là lỗi của server

Chú thích trong file nói rõ: người dùng không làm gì sai và không sửa được gì, nên nó được phân loại server — cùng loại với 500. Hệ quả cụ thể: nó được ghi log ở mức error (bài 09), nó được retry như một lỗi tạm thời? Không — server không nằm trong danh sách tạm thời (bài 07 mục 3.8), nên nó tới người dùng ngay dưới dạng "đã có lỗi xảy ra", kèm correlation id để tra.

3.3 Schema là nguồn, kiểu là hệ quả

packages/contracts/src/customer.ts
export const customerSchema = z.object({
  id: customerIdSchema,
  customerCode: customerCodeSchema,
  fullName: z.string().min(1).max(150),
  email: z.email().max(254),
  phone: z.string().max(32).nullable(),
  dateOfBirth: dateOnlySchema.nullable(),
  gender: genderSchema,
  status: customerStatusSchema,
  address: addressSchema.nullable(),
  avatarUrl: z.string().max(500).nullable(),
  tags: z.array(z.string().min(1).max(40)).max(20),
  createdAt: instantSchema,
  updatedAt: instantSchema,
  createdBy: userIdSchema,
  updatedBy: userIdSchema,
  /** Optimistic-concurrency token. See docs/mock-backend.md. */
  version: versionSchema,
});
export type Customer = z.infer<typeof customerSchema>;

Dòng cuối là cả ý tưởng: kiểu Customer không được viết tay. Nó được suy ra từ schema. Thêm một field vào schema thì kiểu tự có; đổi nullable thành bắt buộc thì mọi chỗ dùng sai sẽ không biên dịch được.

Hướng ngược lại — viết interface trước rồi viết validator riêng — là cách hai thứ lệch nhau: validator cho phép null mà interface nói string, và không ai phát hiện cho tới lúc chạy.

3.4 Branded type: khi hai chuỗi không được lẫn nhau

packages/contracts/src/primitives.ts
export const instantSchema = z.iso.datetime({ offset: false }).brand<'Instant'>();
export type Instant = z.infer<typeof instantSchema>;

export const dateOnlySchema = z.iso.date().brand<'DateOnly'>();
export type DateOnly = z.infer<typeof dateOnlySchema>;

export const customerIdSchema = z.uuid().brand<'CustomerId'>();
export const userIdSchema = z.uuid().brand<'UserId'>();

Cả bốn đều là string lúc chạy. .brand<'X'>() thêm một dấu chỉ tồn tại trong hệ thống kiểu, nên: 

const id: CustomerId = someUserId;   // lỗi biên dịch
const d: DateOnly = customer.createdAt;  // lỗi biên dịch: Instant ≠ DateOnly
const raw: CustomerId = 'abc';       // lỗi biên dịch: chuỗi thường không phải CustomerId

Dòng thứ ba là điều quan trọng nhất: cách duy nhất để có một CustomerId là đi qua schema. Kiểu trở thành bằng chứng rằng giá trị đã được kiểm.

Vì sao Instant và DateOnly phải tách

Chú thích trong file: "a birthday does not move when the viewer does." Một thời điểm (createdAt) là một điểm trên trục thời gian toàn cầu và phải hiển thị theo giờ của người xem. Một ngày lịch (dateOfBirth) không phải — nó là 1990-01-01 ở mọi nơi trên trái đất.

Trộn hai thứ này là bug kinh điển: đưa dateOfBirth qua một new Date() rồi format theo múi giờ, và với người dùng ở phía tây UTC, sinh nhật lùi lại một ngày. Branded type làm trình biên dịch chặn trước khi chuyện đó xảy ra.

3.5 Request và response là hai schema khác nhau

packages/contracts/src/customer.ts
/**
 * Create payload.
 *
 * Everything the server owns is absent: id, code, timestamps, actors, version.
 * A client that could set `createdBy` could forge an audit trail.
 */
export const createCustomerRequestSchema = z.strictObject({
  fullName: z.string().min(1).max(150),
  email: z.email().max(254),
  phone: z.string().max(32).nullable().default(null),
  gender: genderSchema.default('UNSPECIFIED'),
  status: customerStatusSchema.default('PROSPECT'),
  tags: z.array(z.string().min(1).max(40)).max(20).default([]),
  // … không có id, customerCode, createdAt, createdBy, version
});

/**
 * Update payload - a partial, plus the version the client last saw.
 */
export const updateCustomerRequestSchema = z.strictObject({
  fullName: z.string().min(1).max(150).optional(),
  email: z.email().max(254).optional(),
  // … mọi field đều optional
  version: versionSchema,          // ← bắt buộc
});
Quyết định Lý do
Create không có id, createdBy, version "Một client đặt được createdBy là một client giả mạo được nhật ký kiểm toán." Server sở hữu những field đó.
Update có mọi field optional… Vì PATCH gửi phần đã đổi, không gửi cả bản ghi.
…nhưng version bắt buộc "Một update không nói nó dựa trên gì thì không kiểm được độ cũ, và ghi đè âm thầm lên sửa đổi của đồng nghiệp chính là thứ cơ chế này tồn tại để ngăn." Bài 18.
strictObject Field lạ bị từ chối. Gửi dư một field là một lỗi lập trình, và nó nên nổ ngay.
.default(null), .default('PROSPECT') Mặc định nằm trong hợp đồng, nên client và server không cần thoả thuận riêng.

3.6 Một gói, hai người dùng

packages/contracts là một thư viện được biên dịch (ADR-0008), và dist/ không được track trong git. Hệ quả thực tế bạn sẽ gặp: sau khi đổi branch hoặc sửa contract, phải chạy npm run build:contracts, nếu không sẽ thấy does not provide an export named '…'. Lệnh npm start và start:api không build nó.

3.7 Pagination: hợp đồng chung cho mọi danh sách

customers/data/customer.api.ts
/** Built once: constructing a schema per request is measurable at 50,000 rows. */
const customerPageSchema = pageResponseSchema(customerSchema);

list(criteria: CustomerListCriteria): Observable<PageResponse<Customer>> {
  return this.http
    .get<unknown>(this.baseUrl, { params: toHttpParams(criteria) })
    .pipe(withReadPolicy(), map(parseWith(customerPageSchema)));
}

pageResponseSchema là một hàm nhận schema của một phần tử và trả về schema của một trang chứa nó. Nhờ vậy mọi danh sách trong hệ thống có cùng hình dạng — items, totalItems, totalPages — và cùng một kiểu generic PageResponse<T>.

Dòng chú thích phía trên cũng đáng chú ý: schema được dựng một lần ở cấp module, không phải mỗi request. Với 50.000 dòng thì chênh lệch đo được. Đây là loại tối ưu chỉ nên làm khi có số đo — và repo có.

3.8 Một hợp đồng chỉ là lời hứa, không phải đảm bảo

Contract dùng chung khiến client và server khó lệch nhau. Nó không khiến client trở thành đáng tin. Người dùng sửa được JavaScript, gọi API bằng curl, gửi bất cứ body nào họ muốn.

Vì vậy mock API validate độc lập bằng chính schema đó, ở phía nó. Hai lần validate cho hai mục đích khác nhau:

Phía Validate để làm gì
Client (parseWith trên response) Phát hiện server sai hợp đồng, sớm và ở đúng chỗ. Đây là chuyện chất lượng, không phải bảo mật.
Server (validate request) Đây mới là biên bảo mật. Không có gì từ trình duyệt được tin.

Mục 6Đánh đổi & phương án bị loại

Không ánh xạ DTO sang model riêng — ADR-0014

Phương án bị loại: một lớp "domain model" riêng, với mapper từ DTO sang nó. Bị loại vì ở quy mô này mapper chỉ sao chép field, và mỗi field mới phải sửa bốn chỗ. Giá phải trả, và repo nhận nó công khai: kiểu của tầng hiển thị chính là hình dạng trên dây, nên một thay đổi của API lan tới template. ADR ghi điều kiện đổi ý: khi DTO và thứ UI cần thật sự khác nhau.

Contract là package biên dịch, không phải file copy — ADR-0008

Phương án bị loại: mỗi bên tự khai type của mình. Bị loại vì hai bản định nghĩa sẽ lệch, và lệch âm thầm. Giá phải trả: một bước build mà người mới clone luôn quên.

Validate response ở client, dù đã validate ở server

Phương án bị loại: tin server. Bị loại vì "tin" ở đây nghĩa là một lỗi của server biểu hiện thành undefined is not an object trong một template — xa nguyên nhân ba tầng. Giá phải trả: một lần parse mỗi response, và một schema phải giữ đúng.

Mục 7Làm kiểu ngây thơ thì vỡ thế nào

1. Tin http.get<Customer>()

Không có gì kiểm tra. Server trả thiếu một field thì lỗi nổ ở template, với thông báo không liên quan tới nguyên nhân, và stack trace trỏ vào code Angular chứ không vào API.

2. Viết interface tay rồi viết validator riêng

Hai nguồn sự thật. Chúng sẽ lệch ở lần sửa thứ ba, và bên lệch là bên không có test. Luôn z.infer kiểu ra từ schema.

3. Quên gán lại HttpParams 
params.set('search', term);        // SAI - kết quả bị vứt
params = params.set('search', term); // đúng

Tham số không xuất hiện, không lỗi nào được báo, và server trả về cả danh sách.

4. Nối chuỗi vào URL thay vì dùng params

`${url}?search=${term}` — một dấu & hay một dấu cách trong tên khách hàng sẽ phá query string. HttpClient encode đúng; bạn thì sẽ quên một trường hợp.

5. Dùng Date cho dateOfBirth

new Date('1990-01-01') tạo một thời điểm UTC; format theo giờ địa phương ở phía tây UTC cho ra 1989-12-31. Sinh nhật lùi một ngày cho một phần người dùng. Branded type DateOnly tồn tại để trình biên dịch chặn bạn.

6. Quên npm run build:contracts

does not provide an export named '…' sau khi đổi branch hoặc sửa contract. dist/ không được track, và npm start không build nó.

Bài 1 — Chứng minh generic không kiểm tra gì

~20 phút · không sửa code ứng dụng

  1. Chạy app và mock API. Vào trang danh sách.
  2. DevTools → Network → chuột phải một request customers?page=… → "Block request URL". Nạp lại trang và quan sát lỗi hiện ra.
  3. Bỏ chặn. Bây giờ mở apps/mock-api/src/routes/customers.routes.ts, tìm chỗ dựng response của danh sách, và xoá đi field totalPages trước khi trả về.
  4. Nạp lại trang. Người dùng thấy gì? Console nói gì?
  5. git checkout file mock API.
Bạn phải thấy gì, và vì sao bước 3 mới là bài học

Bước 2 là một lỗi mạng bình thường — app hiện trạng thái lỗi, có nút thử lại. Đó là phần dễ.

Bước 3 là một 200 với body sai hợp đồng. Nhờ parseWith, nó bị bắt ngay tại biên và hiện ra như một lỗi server, có log mức error. Thử tưởng tượng nếu không có bước parse: totalPages là undefined, phân trang hiện "trang 2 / undefined", và bạn sẽ đi tìm bug trong component phân trang.

Bài 2 — Đọc schema và trả lời

~30 phút · không sửa code

Mở packages/contracts/src/customer.ts:

  1. Một response có "phone": null — hợp lệ không? Còn "phone": ""? Còn thiếu hẳn field phone?
  2. createCustomerRequestSchema là strictObject. Gửi thêm { "version": 3 } thì sao, và vì sao thiết kế như vậy?
  3. tags cho phép tối đa bao nhiêu phần tử, mỗi phần tử dài tối đa bao nhiêu? Vì sao có giới hạn?
  4. customerCode dùng regex /^C-\d{6}$/ trong khi id là uuid. Vì sao cần cả hai?
Đáp án
  1. null hợp lệ (.nullable()); "" cũng hợp lệ (chỉ có .max(32), không có .min(1)); thiếu hẳn thì không — nullable khác optional. Đây là phân biệt hay bị nhầm nhất khi đọc Zod.
  2. Bị từ chối. Thiết kế vậy vì một client gửi version khi tạo là một client hiểu sai hợp đồng, và im lặng bỏ qua sẽ che giấu hiểu lầm đó cho tới khi nó gây hại ở chỗ khác.
  3. Tối đa 20 tag, mỗi tag 1–40 ký tự. Giới hạn tồn tại vì không có giới hạn nghĩa là một client có thể gửi một mảng một triệu phần tử — đó là một vector từ chối dịch vụ, và nó phải được chặn trong hợp đồng chứ không phải bằng niềm tin.
  4. Chú thích trả lời: id là tay cầm của hệ thống, customerCode là thứ người ta đọc cho nhau qua điện thoại. Hệ thống enterprise gần như luôn có cả hai, và gộp chúng là một cuộc di trú người ta phải hối tiếc.

Bài 3 — Thêm một endpoint, đầu đến cuối

~75 phút · branch learning/* · đây chính là Mốc 2, đạt sớm hơn lịch

Thêm GET /api/customers/stats: trả về số khách hàng theo từng trạng thái.

  1. Contract trước. Thêm customerStatsSchema vào packages/contracts/src/customer.ts và export kiểu bằng z.infer. Nghĩ kỹ hình dạng: một object với ba số, hay một mảng { status, count }? Chọn một và viết lý do.
  2. npm run build:contracts.
  3. Server. Thêm handler trong apps/mock-api/src/routes/customers.routes.ts, dựng response theo đúng schema.
  4. Client. Thêm stats() vào CustomerApi theo đúng khuôn: <unknown>, withReadPolicy(), parseWith.
  5. Test. Một spec với HttpTestingController: đường dẫn đúng, và body sai hợp đồng thành AppError loại server.
  6. npm run lint, typecheck, test sạch.
Bốn câu hỏi để tự chấm, và một gợi ý
  1. Bạn có viết interface CustomerStats bằng tay không? Nếu có — sửa lại thành z.infer. Một nguồn sự thật.
  2. Bạn có khai http.get<CustomerStats> không? Phải là <unknown>.
  3. Bạn chọn withReadPolicy hay withWritePolicy? Đây là GET, nên read — và nếu bạn phải dừng lại nghĩ, đó chính là tác dụng của việc đặt tên theo ý định.
  4. Test của bạn có kiểm trường hợp body sai không? Chỉ kiểm trường hợp đúng là bỏ qua đúng phần mà parseWith tồn tại vì nó.

Gợi ý về hình dạng: mảng { status, count } mở rộng được khi thêm một trạng thái mới mà không đổi kiểu; object ba field thì đọc dễ hơn nhưng mỗi trạng thái mới là một thay đổi phá vỡ. Cả hai đều chấp nhận được — điều quan trọng là bạn biết mình đang đánh đổi gì.

Bài 4 — Branded type cứu bạn

~20 phút · thử rồi xoá

  1. Ở một chỗ bất kỳ trong apps/web, viết: 
    const id: CustomerId = 'abc-123';
const when: DateOnly = someCustomer.createdAt;
  2. Chạy npm run typecheck. Đọc kỹ hai thông báo lỗi.
  3. Bây giờ thử lấy một CustomerId hợp lệ. Có mấy cách? Xoá code thử nghiệm.
Có đúng hai cách, và đó là chủ ý

Một: đi qua schema — customerIdSchema.parse(raw), thường là gián tiếp qua parseWith trên cả response. Hai: lấy từ một giá trị đã được kiểm, ví dụ customer.id.

Không có đường thứ ba, và đó chính là giá trị: kiểu trở thành bằng chứng rằng giá trị đã đi qua kiểm tra. Trong một hệ thống lớn, đó là khác biệt giữa "chắc là đã validate ở đâu đó" và "trình biên dịch nói rằng rồi".

Mục 11Tự kiểm tra

1. Vì sao repo khai http.get<unknown> thay vì kiểu thật?

Vì generic bị xoá lúc chạy — khai kiểu thật là một lời hứa không ai kiểm. unknown nói thật rằng chưa biết gì, rồi Zod biến nó thành kiểu đã xác nhận.

2. nullable khác optional thế nào?

nullable: field phải có mặt, giá trị được phép là null. optional: field có thể vắng mặt. customerSchema.phone là nullable — thiếu hẳn field đó là sai hợp đồng.

3. Vì sao kiểu phải suy ra từ schema chứ không viết tay?

Vì hai bản khai sẽ lệch nhau, và lệch âm thầm. z.infer<typeof schema> cho một nguồn sự thật duy nhất: đổi schema thì mọi chỗ dùng sai lập tức không biên dịch được.

4. Branded type giải quyết vấn đề gì?

Ngăn lẫn lộn giữa các chuỗi có ý nghĩa khác nhau (CustomerId vs UserId, Instant vs DateOnly), và biến kiểu thành bằng chứng rằng giá trị đã đi qua schema — chuỗi thường không gán vào đó được.

5. Một response 200 với body sai hợp đồng: ai sai, người dùng thấy gì?

Server sai. Người dùng không làm gì sai và không sửa được, nên nó được phân loại server — hiện ra như một lỗi chung kèm correlation id, và được ghi log ở mức error. Nó không được retry.

6. Vì sao schema request khác schema response?

Vì client không sở hữu mọi field. Create không có id, createdBy, version — một client đặt được createdBy là giả mạo được nhật ký kiểm toán. Update thì mọi field optional (vì là PATCH) nhưng version bắt buộc.

7. Validate ở client có phải là bảo mật không?

Không. Nó phát hiện server sai hợp đồng — chuyện chất lượng. Biên bảo mật nằm ở server, nơi cùng schema đó kiểm mọi request đến, vì không gì từ trình duyệt được tin.

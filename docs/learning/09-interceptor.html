Interceptor

Năm hàm, mỗi hàm chưa tới sáu mươi dòng, và mọi request HTTP trong ứng dụng đi qua cả năm. Bài này đọc từng cái — nhưng phần đáng giá nhất không phải từng cái, mà là thứ tự: ở đây nó không phải chi tiết cài đặt mà là một hợp đồng, và mỗi vị trí có một lập luận viết sẵn trong code.

  • Chuyển được sang dự án thật
  • Chặng 2 · hướng tới Mốc 2
  • ~2,5 giờ đọc + 90 phút làm

Mục 0Từ vựng

Từ Nghĩa
HttpInterceptorFn Một hàm (req, next) => Observable<HttpEvent>. Angular hiện đại dùng hàm, không phải class.
next(req) Chuyển request cho mắt kế tiếp trong chuỗi, và trả về luồng response của nó.
req.clone({ … }) Request là bất biến. Sửa nghĩa là tạo bản sao có sửa đổi.
HttpContext Túi dữ liệu có kiểu đi theo một request, không gửi lên server. Cách các interceptor nói chuyện với nhau.
HttpContextToken Khoá có kiểu cho túi đó, kèm giá trị mặc định.
HttpEvent Mọi thứ phát ra trên đường về: tiến độ tải lên, header đã nhận, và cuối cùng là HttpResponse.
HttpBackend Mắt cuối cùng — thứ thực sự gửi request đi (fetch hoặc XHR).
Double-submit CSRF Một token vừa nằm trong cookie đọc được, vừa phải được echo lên header; server so hai cái.
Single-flight Nhiều người cùng cần một việc thì chỉ chạy một lần, mọi người chờ chung kết quả.

Mục 1Sau bài này bạn làm được gì

  • Viết một interceptor mới và biết đặt nó ở đâu trong chuỗi.
  • Giải thích được từng vị trí trong chuỗi năm cái của repo — không phải "theo thói quen" mà bằng chuyện gì hỏng nếu đổi chỗ.
  • Dùng HttpContext để truyền một cờ cho một request cụ thể.
  • Nói được ba thứ không thuộc về interceptor, và chúng ở đâu.

Mục 2Dịch từ backend sang Angular — và chỗ phép so sánh sai

Bạn đã biết Ở đây Chỗ phép so sánh sai
Servlet Filter chain Interceptor chain Gần như y hệt về cơ chế: xuống rồi lên, chain.doFilter ↔ next(req). Khác hẳn về thẩm quyền: filter của bạn là biên bảo mật, cái này chạy trong máy người dùng.
HandlerInterceptor của Spring Cùng ý tưởng Spring có preHandle/postHandle tách rời. Ở đây một hàm lo cả hai chiều, vì chiều về là một Observable bạn pipe vào.

ThreadLocal / request attributes HttpContext Cùng mục đích — mang dữ liệu theo một request mà không gửi lên server — nhưng có kiểu, nên không ai đọc nhầm khoá.
Một câu để nhớ cả bài

Filter của bạn bảo vệ. Interceptor ở đây chăm sóc: nó đóng dấu id để tra cứu được, ghi log, làm mới phiên hết hạn, đính kèm token CSRF, và dịch lỗi sang ngôn ngữ của ứng dụng. Không cái nào trong năm việc đó là một phòng tuyến — phòng tuyến nằm ở server.

Mục 3Cơ chế

3.1 Một interceptor là một hàm

hình dạng nhỏ nhất
export const myInterceptor: HttpInterceptorFn = (req, next) => {
  // 1. trước khi gửi: sửa request (phải clone)
  const changed = req.clone({ setHeaders: { 'X-Thing': 'value' } });

  // 2. chuyển cho mắt kế tiếp
  return next(changed).pipe(
    // 3. trên đường về: quan sát hoặc biến đổi response
    tap({ next: (event) => { … } }),
  );
};

Đăng ký bằng withInterceptors([...]) trong provideHttpClient. Thứ tự trong mảng là thứ tự chạy.

Interceptor chạy trong injection context, nên gọi inject() trong thân hàm được — đó là cách requestLoggingInterceptor lấy Logger.

1 · correlationIdInterceptor — đóng dấu để tra cứu được

core/http/correlation-id.interceptor.ts — toàn bộ
export const CORRELATION_ID_HEADER = 'X-Correlation-Id';

export const CORRELATION_ID = new HttpContextToken<CorrelationId | null>(() => null);

export const correlationIdInterceptor: HttpInterceptorFn = (req, next) => {
  const correlationId = newCorrelationId();

  return next(
    req.clone({
      setHeaders: { [CORRELATION_ID_HEADER]: correlationId },
      context: req.context.set(CORRELATION_ID, correlationId),
    }),
  );
};
Dòng Nghĩa
setHeaders Id đi lên server, nơi mock API ghi nó vào log của chính nó.
context.set(CORRELATION_ID, …) Id cũng ở lại phía client, dưới dạng một giá trị có kiểu. Chú thích nói vì sao cả hai: header cũng đi được, nhưng context sống như một giá trị mà phần còn lại của chuỗi đọc được không phải parse lại header.
Đứng đầu chuỗi Để mọi interceptor khác đọc được id. Đứng thứ hai thì cái thứ nhất đã ghi log mà không có id.

2 · requestLoggingInterceptor — quan sát, không can thiệp

core/http/request-logging.interceptor.ts — rút gọn
const UNEXPECTED_KINDS: ReadonlySet<string> = new Set(['server', 'network', 'timeout', 'unknown']);

export const requestLoggingInterceptor: HttpInterceptorFn = (req, next) => {
  const logger = inject(Logger);
  const monitor = inject(PerformanceMonitor);
  const started = performance.now();

  const fields = () => ({
    method: req.method,
    url: withoutQuery(req.url),
    durationMs: Math.round(performance.now() - started),
    correlationId: req.context.get(CORRELATION_ID) ?? undefined,
  });

  return next(req).pipe(
    tap({
      next: (event) => {
        if (event instanceof HttpResponse) {
          logger.debug('HTTP request completed', { …fields(), status: event.status });
          monitor.recordApiCall(…);
        }
      },
      error: (error: unknown) => {
        const kind = isAppError(error) ? error.kind : 'unknown';
        const level = UNEXPECTED_KINDS.has(kind) ? 'error' : 'warn';
        logger[level]('HTTP request failed', { …fields(), kind, status });
      },
      unsubscribe: () => logger.debug('HTTP request cancelled', fields()),
    }),
  );
};

function withoutQuery(url: string): string {
  const query = url.indexOf('?');
  return query === -1 ? url : url.slice(0, query);
}

Bốn quyết định trong file này đáng học, và không cái nào hiển nhiên:

Quyết định Lý do
Ba kết cục, ba mức log Xong → debug; bị huỷ → debug (một tìm kiếm bị thay thế là store làm đúng việc, không phải lỗi); thất bại → tuỳ loại.
warn cho 401/403/404/409/422/429, error cho phần còn lại "Một 404, một 409, một quyền bị từ chối là API trả lời đúng như thiết kế, và tính năng đã hỏi sẽ xử lý nó." Mức error được giữ cho thứ không ai xử lý tốt được — để một cảnh báo trên error có nghĩa.
withoutQuery(req.url) ?search=nguyen%20van%20a là tên một khách hàng, và tìm theo email là một địa chỉ email. Đường dẫn đủ để nhận ra endpoint — đó là thứ người vận hành cần.
Không log body, không log header Đó là thứ giữ mật khẩu và token CSRF ra khỏi mọi dòng log.
unsubscribe trong tap

Ít người biết tap có callback này. Nó chạy khi ai đó huỷ đăng ký — tức là khi switchMap trong store bỏ một request. Nhờ nó, một request bị huỷ được ghi là "cancelled" chứ không im lặng biến mất, và không được tính vào số đo độ trễ API: thời gian đó là thời gian người dùng chờ trước khi đổi ý, không phải thời gian server xử lý.

3 · authRefreshInterceptor — làm mới phiên, một lần, thử lại một lần

core/http/auth-refresh.interceptor.ts — toàn bộ phần thân
export const authRefreshInterceptor: HttpInterceptorFn = (req, next) => {
  if (req.context.get(SKIP_SESSION_REFRESH)) {
    return next(req);
  }

  const session = inject(SessionService);
  const sentAt = session.generation;

  return next(req).pipe(
    catchError((error: unknown) => {
      if (!isAppError(error) || error.kind !== 'authentication') {
        return throwError(() => error);
      }

      return session.renewAfter(sentAt).pipe(
        catchError(() => throwError(() => error)),
        switchMap(() => next(req)),
      );
    }),
  );
};
Dòng Nghĩa
SKIP_SESSION_REFRESH Một cờ trong HttpContext: chính request /auth/refresh không được phép tự làm mới khi nó nhận 401 — đó là đệ quy vô hạn.
const sentAt = session.generation Ghi lại "thế hệ" của phiên lúc request rời đi. Đây là cách phát hiện một cuộc đua: nếu generation đã đổi khi 401 về, thì ai đó đã làm mới trong lúc request bay — chỉ cần thử lại, không làm mới lần nữa.
error.kind !== 'authentication' Nó đọc loại, không đọc status code — vì nó nằm trên errorMapping trong chuỗi.
catchError(() => throwError(() => error)) Refresh hỏng thì người gọi nhận lỗi gốc. Nó hỏi về một khách hàng, không hỏi về refresh — và "phiên của bạn đã kết thúc" là bản tường thuật đúng về chuyện đã xảy ra với request của nó.
switchMap(() => next(req)) Thử lại đúng một lần. 401 lần hai là câu trả lời, không phải triệu chứng — nếu không, một server từ chối token mới sẽ bị hỏi mãi mãi.
Vì sao retry cả lệnh ghi ở đây là an toàn

Bài 07 nói lệnh ghi không bao giờ được retry. Ở đây nó được, và chú thích đưa ra lập luận cụ thể: một 401 do requireAuth quyết định trước khi bất kỳ handler nào chạy, nên request nhận 401 đã không thay đổi gì trên server. Thử lại không thể áp dụng hai lần.

Đây là kiểu lập luận bạn nên tập: không phải "retry xấu" hay "retry tốt", mà "ở chỗ này, với lý do này, nó an toàn".

4 · csrfInterceptor — nửa phía client của double-submit

core/http/csrf.interceptor.ts — rút gọn
const SAFE_METHODS = new Set(['GET', 'HEAD', 'OPTIONS']);

export const csrfInterceptor: HttpInterceptorFn = (req, next) => {
  const isBrowser = inject(IS_BROWSER);
  const document = inject(DOCUMENT);

  if (!isBrowser || SAFE_METHODS.has(req.method) || !isSameOrigin(req.url)) {
    return next(req);
  }

  const token = readCookie(document.cookie, CSRF_COOKIE_NAME);
  if (!token) {
    // Not an error to raise here: the request goes out and the server answers
    // 403, which the error taxonomy already maps.
    return next(req);
  }

  return next(req.clone({ setHeaders: { [CSRF_HEADER_NAME]: token } }));
};

function isSameOrigin(url: string): boolean {
  return url.startsWith('/') && !url.startsWith('//');
}

Cơ chế: cookie phiên là HttpOnly + SameSite=Lax, nên một form từ site khác không đọc được nó nhưng vẫn khiến trình duyệt gửi nó. Token thứ hai bịt chỗ đó: nó đọc được bởi script cùng origin và phải được echo lên header — việc mà trang của kẻ tấn công không làm được. Server so hai cái.

Quyết định Lý do
Chỉ phương thức không an toàn "Một GET cần bảo vệ sẽ là lỗi thiết kế của API, không phải thứ vá ở đây."
Chỉ request cùng origin Token là một credential; gửi nó tới bất kỳ host nào mà apiBaseUrl trỏ tới là trao nó cho host đó.
!url.startsWith('//') //evil.test/api là URL khác origin trông như tương đối. Loại trừ tường minh, không dựa vào dấu gạch chéo đầu.
Không có token thì vẫn gửi Để server trả 403 và lý do thật — là không có phiên — lộ ra. Thất bại tại chỗ sẽ che mất nguyên nhân.
Dưới authRefresh Để request được thử lại được đóng dấu lại từ cookie như nó đang là bây giờ — sau khi refresh đã xoay token.

5 · errorMappingInterceptor — biên của ngôn ngữ

core/http/error-mapping.interceptor.ts — toàn bộ phần thân
export const errorMappingInterceptor: HttpInterceptorFn = (req, next) => {
  return next(req).pipe(
    catchError((error: unknown) => {
      const correlationId = req.context.get(CORRELATION_ID) ?? undefined;

      const mapped =
        error instanceof HttpErrorResponse
          ? mapHttpError(error, correlationId)
          : appError('unknown', { correlationId, cause: error });

      return throwError(() => mapped);
    }),
  );
};

Mười dòng, và nó là lý do không một feature nào trong repo biết 409 nghĩa là gì — chúng chỉ biết conflict. Nó cũng là nơi correlation id được gắn vào lỗi, nên khi người dùng báo lỗi, màn hình có một mã tra được trong log của cả hai phía.

Một trách nhiệm, và lịch sử của nó

Chú thích ghi lại một thay đổi: tới phase 3, interceptor này còn ghi log lỗi nữa. Việc đó được chuyển sang requestLoggingInterceptor, vì một interceptor vừa phân loại vừa báo cáo sẽ ghi một 401 — thứ mà refresh interceptor ngay sau đó lặng lẽ khắc phục — như thể đó là lỗi người dùng đã thấy.

Đây là "một trách nhiệm cho một thứ" ở dạng cụ thể nhất: không phải nguyên tắc trừu tượng, mà là một dòng log sai mà người ta đã phải sửa.

3.4 Thứ tự là một hợp đồng — từng cặp một

Cặp Nếu đảo lại thì sao
correlationId trước mọi thứ Interceptor nào chạy trước nó sẽ đọc context rỗng — log không có id, lỗi không có id để tra.
requestLogging trên authRefresh Đảo lại: một request được làm mới phiên rồi thử lại sẽ thành hai dòng log — một 401 "lỗi" mà thật ra đã được khắc phục, và một request thành công. Thời lượng thật mà người dùng chờ biến mất.
authRefresh trên csrf Đảo lại: request thử lại mang token CSRF cũ, chụp từ trước khi refresh xoay cookie. Server từ chối 403, và triệu chứng là "thỉnh thoảng lưu không được sau khi để máy một lúc".
errorMapping cuối cùng Đặt nó đầu chuỗi: mọi tầng trên phải suy luận theo status code. authRefresh sẽ phải biết 401, requestLogging sẽ phải tự phân loại, và mỗi feature sẽ học lại ý nghĩa của từng mã.

3.5 HttpContext: nói chuyện với chính chuỗi

khuôn, từ hai chỗ trong repo
// khai một khoá có kiểu, kèm mặc định
export const SKIP_SESSION_REFRESH = new HttpContextToken<boolean>(() => false);

// người gọi bật nó cho đúng một request
this.http.post('/auth/refresh', {}, {
  context: new HttpContext().set(SKIP_SESSION_REFRESH, true),
});

// interceptor đọc
if (req.context.get(SKIP_SESSION_REFRESH)) {
  return next(req);
}

Vì sao không dùng một header: header đi lên server, và đây là chuyện nội bộ của client. Vì sao không dùng một biến toàn cục: nhiều request chạy song song, và một cờ toàn cục sẽ áp nhầm cho request khác. Context đi theo từng request và có kiểu.

Mục 5Sơ đồ

5.1 Một request hết phiên, từ đầu tới cuối

Mục 6Đánh đổi & phương án bị loại

Thứ tự được viết thành tài liệu, không để ngầm hiểu — ADR-0017

Phương án bị loại: để thứ tự là chi tiết cài đặt. Bị loại vì nó không phải — bốn cặp ở mục 3.4 cho thấy mỗi hoán vị đều hỏng một thứ cụ thể. Giá phải trả: thêm một ràng buộc phải nhớ khi thêm interceptor mới. Repo trả nó bằng chú thích dài trong http.providers.ts và bằng những test khẳng định hệ quả của thứ tự — mục 8.

Retry được phép ở interceptor refresh

Ngoại lệ duy nhất với luật "không retry lệnh ghi", và lập luận an toàn được viết ngay chỗ nó được đưa ra: 401 do requireAuth quyết định trước khi handler chạy, nên không gì đã thay đổi. Đây là cách xử lý một ngoại lệ đúng — không im lặng, mà kèm lý lẽ.

Không có interceptor nào gắn credential

Phương án bị loại: bearer token trong localStorage, gắn bằng interceptor — cách gần như mọi tutorial dạy. Bị loại vì token trong localStorage đọc được bằng bất kỳ script nào chạy trên trang, nên một lỗ XSS thành một lần chiếm phiên. Cookie HttpOnly thì script không đọc được. Giá phải trả: phải có CSRF, và phải cùng origin.

Mục 7Làm kiểu ngây thơ thì vỡ thế nào

1. Sửa request thay vì clone

req.headers.set(...) trả về headers mới và vứt đi — request không đổi. Không lỗi nào. Header đơn giản là không tới server, và bạn sẽ đi tìm bug ở phía backend.

2. Quên return next(req) ở nhánh sớm

Mọi nhánh của interceptor phải trả về một Observable. Thiếu một nhánh return thì request đó không bao giờ được gửi, và người gọi chờ mãi mãi — không lỗi, không timeout, chỉ là một spinner không bao giờ dừng.

3. Interceptor refresh không chặn chính request refresh

/auth/refresh trả 401 → interceptor gọi refresh → request đó trả 401 → gọi refresh… Đệ quy vô hạn, trình duyệt treo. SKIP_SESSION_REFRESH tồn tại vì đúng chuyện này.

4. Mỗi 401 tự gọi refresh của riêng nó

Mười request hết hạn cùng lúc là mười lần làm mới. Vì refresh token bị xoay vòng sau mỗi lần dùng, chín cái sau trình một token đã tiêu — server coi là tấn công replay và chấm dứt phiên. Người dùng bị đăng xuất đúng lúc hệ thống đang cố giữ họ đăng nhập.

5. Log cả URL kèm query string

Tên khách hàng và địa chỉ email vào log, rồi vào hệ thống thu thập log, rồi được giữ ba tháng. Đây là một sự cố dữ liệu cá nhân, và nó bắt đầu bằng một dòng logger.debug(req.url) trông vô hại.

6. Thêm interceptor mới vào cuối mảng cho tiện

Cuối mảng nghĩa là dưới errorMapping, nơi lỗi vẫn còn là HttpErrorResponse. Nếu interceptor của bạn đọc error.kind, nó sẽ luôn thấy undefined. Vị trí phải được chọn, không phải mặc định.

Mục 10Bài tập

Bài 1 — Nhìn chuỗi làm việc

~25 phút · không sửa code

  1. Chạy app, đăng nhập, mở DevTools → Network và console. Đặt log level về debug nếu cần (xem config.json).
  2. Bấm sang trang 2. Trong Network, xem header của request.
  3. Sửa một khách hàng rồi lưu. So sánh header của PATCH với header của GET — khác nhau ở đâu?
  4. Trong console, tìm dòng log của mỗi request. Nó chứa những gì?
  5. Gõ nhanh vào ô tìm kiếm rồi dừng. Tìm dòng log HTTP request cancelled.
Bạn phải thấy gì

GET có X-Correlation-Id nhưng không có header CSRF. PATCH có cả hai — vì CSRF chỉ đóng dấu phương thức không an toàn.

Dòng log chứa method, đường dẫn không có query string, thời lượng, correlation id, và status. Không có body, không có header. Đó chính là phần "cố ý không ghi" ở mục 3.3.

Và dòng cancelled đến từ callback unsubscribe trong tap — bằng chứng rằng switchMap đã huỷ thật.

Bài 2 — Đảo thứ tự và quan sát hậu quả

~30 phút · sửa rồi hoàn nguyên

  1. Trong http.providers.ts, chuyển errorMappingInterceptor lên đầu mảng.
  2. Chạy npm test --workspace @ecm/web. Ghi lại test nào đổ và tên của nó.
  3. Hoàn nguyên. Bây giờ đổi chỗ authRefreshInterceptor và csrfInterceptor.
  4. Chạy test lại. Suy luận: với thứ tự này, một request được thử lại sau refresh sẽ mang token CSRF nào?
  5. git checkout.
Bạn phải thấy gì

Bước 2: điều cần suy luận quan trọng hơn danh sách test đổ. authRefresh đọc error.kind; với thứ tự mới nó nhận một HttpErrorResponse chưa được map, nên isAppError trả false và nó không bao giờ làm mới phiên. Triệu chứng trên production: phiên hết hạn thì người dùng bị văng ra, thay vì được làm mới âm thầm.

Nếu có test nào đổ, đọc tên nó và đối chiếu với suy luận trên. Nếu không test nào đổ, đó cũng là một phát hiện đáng giá — nó nói rằng hệ quả này chưa được một cổng nào canh, và viết test đó là một đóng góp thật cho repo.

Bước 4: token cũ — chụp trước khi refresh xoay cookie. Server trả 403. Và đây là loại bug chỉ xuất hiện sau khi để máy một lúc, nên nó qua được mọi lần test thủ công.

Bài 3 — Viết một interceptor mới

~60 phút · branch learning/*

Viết slowRequestInterceptor: cảnh báo khi một request mất hơn 3 giây.

  • Ghi logger.warn với method, đường dẫn (không query), thời lượng, correlation id.
  • Không cảnh báo cho request bị huỷ.
  • Cho phép một request tự miễn bằng một HttpContextToken — ví dụ export CSV, vốn chậm là bình thường.
  • Đặt nó ở đúng vị trí trong chuỗi, và viết lý do.
  • Một spec: nhanh thì không cảnh báo, chậm thì có, bị huỷ thì không.
Vị trí đúng, và hai chỗ dễ sai

Vị trí: ngay cạnh requestLogging, tức là trên authRefresh. Lý do giống hệt: bạn muốn đo thời gian người dùng thật sự chờ, bao gồm cả lần refresh và thử lại. Đặt dưới authRefresh thì một request chậm vì phải làm mới phiên sẽ không bị phát hiện.

Dễ sai 1: dùng setTimeout để đếm. Không cần — đo performance.now() ở đầu và trong tap, giống requestLogging. Một timer còn phải nhớ dọn.

Dễ sai 2: quên nhánh unsubscribe. Một request bị switchMap huỷ sau 5 giây không phải request chậm — người dùng đã đổi ý. Cảnh báo cho nó là tạo nhiễu.

Bài 4 — Lần theo một lỗi 409 qua cả chuỗi

~25 phút · đọc code

Mock API có cơ chế gây lỗi theo yêu cầu qua header x-mock-scenario (xem docs/mock-backend.md). Không cần chạy — chỉ cần đọc và trả lời:

  1. Một PATCH nhận 409. Nó đi qua năm interceptor theo thứ tự nào trên đường về, và mỗi cái làm gì?
  2. Nó có bị retry không? Ở đâu quyết định điều đó?
  3. Nó được ghi log ở mức nào, và vì sao không phải mức kia?
  4. Người dùng cuối cùng thấy gì, và ai quyết định câu chữ đó?
Đáp án
  1. errorMapping (5) biến HttpErrorResponse thành AppError kind conflict, gắn correlation id → csrf (4) không làm gì trên đường về → authRefresh (3) thấy kind khác 'authentication' nên ném tiếp → requestLogging (2) ghi một dòng → correlationId (1) không làm gì.
  2. Không. withWritePolicy không có retry nào cả — và kể cả với withReadPolicy thì isTransient cũng loại conflict ra.
  3. warn. conflict không nằm trong UNEXPECTED_KINDS — đây là API trả lời đúng như thiết kế, và form sẽ xử lý nó. Mức error được giữ cho thứ không ai xử lý tốt được, để cảnh báo trên error còn có nghĩa.
  4. Một thông báo rằng ai đó đã sửa bản ghi này, kèm lựa chọn tải lại — do trang form quyết định, dựa trên kind. Câu chữ nằm trong file dịch, không nằm trong lỗi. Bài 10 và 18.

Mục 11Tự kiểm tra

1. Vì sao phải req.clone()?

Request là bất biến. req.headers.set(...) trả về một headers mới và không đổi request — một lỗi im lặng. clone tạo bản sao có sửa đổi, và đó là thứ bạn truyền cho next.

2. Vì sao errorMapping ở cuối chuỗi?

Để mọi tầng trên nó chỉ suy luận theo loại lỗi. authRefresh cần biết "phiên hết hạn", không cần biết "401"; mỗi feature cần biết "conflict", không cần biết "409".

3. Vì sao requestLogging ở trên authRefresh?

Để một request được làm mới phiên rồi thử lại là một dòng log với thời lượng thật người dùng chờ — thay vì một "lỗi" 401 đã được khắc phục cộng một request thành công.

4. HttpContext dùng để làm gì, khác header ở đâu?

Mang dữ liệu có kiểu theo một request, phía client, không gửi lên server. Header thì đi lên server. Biến toàn cục thì áp nhầm cho request song song. SKIP_SESSION_REFRESH và CORRELATION_ID là hai ví dụ.

5. Vì sao retry một lệnh ghi lại an toàn trong interceptor refresh?

Vì 401 được requireAuth quyết định trước khi handler chạy, nên request đó không thay đổi gì trên server. Thử lại không thể áp dụng hai lần. Lập luận này chỉ đúng cho 401 — không mở rộng ra lỗi khác.

6. Vì sao không có interceptor nào gắn Authorization?

Vì credential là cookie HttpOnly do trình duyệt tự đính kèm, và JavaScript không đọc được nó. Đổi lại phải có CSRF và phải cùng origin. Đây là lựa chọn, không phải thiếu sót.

7. Ba thứ không thuộc về interceptor là gì?

Timeout/retry (thuộc về request-policy, theo từng endpoint), gắn credential (không tồn tại — cookie lo), và quyết định điều hướng khi phiên hết (thuộc về SessionService.ended$, để mười request hỏng cùng lúc chỉ chuyển trang một lần).

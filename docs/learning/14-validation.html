Validation

Viết một validator mất năm phút. Phần khó là ba câu hỏi còn lại: khi nào được hiện lỗi, câu nào trong số nhiều lỗi cùng lúc, và làm sao lỗi của server hoà vào cùng một chỗ mà không để lọt một chữ tiếng Anh nào ra màn hình.

  • Chuyển được sang dự án thật
  • Chặng 3 · hướng tới Mốc 3
  • ~2,5 giờ đọc + 2 giờ làm

ValidationErrors Một object: khoá là tên lỗi, giá trị là chi tiết — { tooLong: { max: 150 } }.

Mục 1Sau bài này bạn làm được gì

  • Viết cả ba loại validator, và biết loại nào thuộc về đâu.
  • Viết một async validator không treo form khi mạng hỏng và không kẹt ở PENDING.
  • Quyết định được khi nào hiện lỗi và hiện lỗi nào, khi một ô có nhiều lỗi.
  • Đưa lỗi 422 của server vào đúng ô, bằng ngôn ngữ người dùng, mà không hiển thị một chữ nào do backend viết.

3.2 Validator là một hàm thuần

customers/customer-form/customer-form-model.ts
function maxLength(max: number) {
  return (control: { value: unknown }): ValidationErrors | null => {
    const value = String(control.value ?? '');
    return value.length > max ? { tooLong: { max } } : null;
  };
}

function emailFormat(control: { value: unknown }): ValidationErrors | null {
  const value = String(control.value ?? '').trim();
  if (!value) {
    return null;
  }
  // One `@`, something either side, and a dot in the domain. Deliberately not
  // an RFC 5322 regular expression: those reject addresses that work and are
  // impossible to read. The server validates properly; this is a typo catcher.
  return /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(value) ? null : { invalidEmail: true };
}
Chi tiết Nghĩa
{ tooLong: { max } } Tên lỗi, kèm tham số. Tham số đó sẽ đi thẳng vào câu dịch: "tối đa {{max}} ký tự". Nhờ vậy giới hạn không bị lặp lại trong file ngôn ngữ.
if (!value) return null Ô rỗng không phải lỗi định dạng. "Bắt buộc" là việc của Validators.required. Thiếu dòng này thì một ô tuỳ chọn để trống sẽ báo "email không hợp lệ".
control: { value: unknown } Không khai AbstractControl mà chỉ khai đúng thứ cần. Nhờ vậy test gọi nó bằng { value: 'x' } — không cần dựng control thật.
maxLength là một factory Trả về validator, nên giới hạn được truyền vào tại chỗ dùng. Cùng khuôn với requirePermission() ở bài 16.

3.3 Cross-field: quy tắc không thuộc về ô nào

customers/customer-form/customer-form-model.ts
/**
 * Cross-field rule: an address is all or nothing.
 *
 * Starting an address and leaving out the city produces a record that cannot
 * be posted to anyone, so the moment any part is filled in, the parts that
 * make it deliverable become required. This is on the group rather than on the
 * controls because no single control can answer the question.
 */
function addressCompleteness(group: {
  value: Partial<Record<keyof CustomerAddressControls, string>>;
}): ValidationErrors | null {
  const value = group.value;
  const entries = Object.values(value).map((field) => (field ?? '').trim());
  if (entries.every((field) => field === '')) {
    return null;                                    // chưa ai điền gì → hợp lệ
  }

  const missing = (['line1', 'city', 'country'] as const).filter(
    (field) => !(value[field] ?? '').trim(),
  );
  return missing.length ? { addressIncomplete: { fields: missing } } : null;
}

Câu "no single control can answer the question" là tiêu chí quyết định. Ô city không biết nó có bắt buộc hay không — điều đó phụ thuộc vào việc ô line1 có gì. Chỉ nhóm mới trả lời được.

cùng file — quy tắc trên cả form
function phoneRequiredWhenActive(group: {
  value: { status?: CustomerStatus; phone?: string };
}): ValidationErrors | null {
  const { status, phone } = group.value;
  return status === 'ACTIVE' && !(phone ?? '').trim() ? { phoneRequiredWhenActive: true } : null;
}
Một câu trung thực trong chú thích

"It is checked again on the server — or would be, in a real system; here it is the client's rule, and saying so is better than implying the server enforces it."

Đây là mẫu mực của việc ghi tài liệu trung thực: repo không giả vờ rằng mock API kiểm quy tắc này. Nếu bạn mang khuôn này sang dự án thật, nhớ rằng một quy tắc nghiệp vụ chỉ sống ở client là một quy tắc có thể bị bỏ qua bằng curl.

3.4 Async validator: bốn quyết định trong mười dòng

customers/customer-form/email-availability.validator.ts — toàn bộ phần thân
export function emailAvailabilityValidator(
  store: CustomerStore,
  excludeId: () => CustomerId | null,
): AsyncValidatorFn {
  return (control) => {
    const email = String(control.value ?? '').trim();
    const blockedBySyncErrors =
      control.hasError('required') ||
      control.hasError('invalidEmail') ||
      control.hasError('tooLong');

    if (!email || blockedBySyncErrors) {
      return of(null);
    }

    return timer(EMAIL_CHECK_DEBOUNCE_MS).pipe(
      switchMap(() => store.isEmailAvailable(email, excludeId())),
      map((available) => (available ? null : { emailTaken: true })),
      catchError(() => of(null)),
      // An async validator must complete, or the control stays PENDING for
      // ever and the submit button never enables.
      first(),
    );
  };
}
Quyết định Lý do, theo chú thích
timer(400) ở đầu pipeline Angular chạy lại async validator sau mỗi lần giá trị đổi và unsubscribe lượt trước. Nên một timer dẫn đầu nghĩa là request chỉ được gửi khi gõ đã ngừng — và việc huỷ đến miễn phí từ framework, không phải từ một cờ so sánh id request.
catchError(() => of(null)) Mạng hỏng thì câu trả lời trung thực là "tôi không biết". Chặn người dùng lưu vì điều đó còn tệ hơn để server quyết định — mà server sẽ quyết định, bằng một 409 mà trang xử lý được.
Bỏ qua khi validator sync đã báo lỗi Hỏi xem "không phải email" có bị trùng không là tốn một request để trả lời một câu hỏi người dùng đã được báo rồi.
first() Async validator bắt buộc phải hoàn tất. Không thì control kẹt PENDING vĩnh viễn và nút Lưu không bao giờ bật.
excludeId: () => CustomerId | null Một hàm, không phải giá trị — vì id chỉ biết sau khi bản ghi được nạp, còn validator được gắn vào form sớm hơn. Khi sửa, email của chính bản ghi này không được coi là trùng.

Hai quyết định, và cả hai đều về trải nghiệm chứ không về kỹ thuật:

  • Một lỗi tại một thời điểm. Nói với người dùng hai điều về một ô là họ không đọc điều nào. Thứ tự ưu tiên cố định, và "bắt buộc" đứng đầu vì nó là thứ phải sửa trước.
  • Chỉ hiện khi người dùng đã có cơ hội: đã rời khỏi ô (touched), hoặc đã bấm Lưu (submitted). Dùng dirty ở đây là bug — bài 13 mục 3.4.

3.6 Lỗi của server, vào đúng ô

customers/customer-form/validation-messages.ts
export function applyServerFieldErrors(
  form: CustomerForm,
  fieldErrors: ValidationError['fieldErrors'],
  fieldIssues: ValidationError['fieldIssues'] = {},
): string[] {
  const unmatched: string[] = [];
  const paths = new Set([...Object.keys(fieldErrors), ...Object.keys(fieldIssues)]);

  for (const path of paths) {
    const control = form.get(path);
    if (control) {
      control.setErrors({
        ...(control.errors ?? {}),
        [SERVER_ERROR]: serverErrorFor(path, fieldIssues[path]?.[0]),
      });
      // Marked touched so the message is visible immediately: the user has
      // already pressed save, so waiting for a blur would show nothing.
      control.markAsTouched();
    } else {
      unmatched.push(path);
    }
  }

  return unmatched;
}
Dòng Nghĩa
form.get(path) path là đường dẫn có dấu chấm — address.city. Contract chọn cách viết đó chính vì form.get hiểu nó trực tiếp. Hai hệ thống khớp nhau ở một quy ước đặt tên.
...(control.errors ?? {}) Giữ các lỗi sẵn có, chỉ thêm lỗi của server. Gán đè sẽ xoá kết quả của validator client.
markAsTouched() Để thông báo hiện ngay. Người dùng đã bấm Lưu rồi, nên chờ họ blur là chờ một việc sẽ không xảy ra.
unmatched được trả về Đường dẫn không khớp control nào — kể cả khoá _ mà envelope dùng cho lỗi của cả payload — được trả về để trang hiện phía trên form, thay vì bị mất.

3.7 Mã lý do, không phải câu chữ

customers/customer-form/validation-messages.ts — chú thích đầu file
`FieldErrors` maps a dotted field path to messages, and those messages are
documented in `@ecm/contracts` as developer-facing: they are English
sentences produced by the schema, they name internal field paths, and they
cannot be translated. Rendering them would break two rules at once - no raw
backend errors, and no untranslated user-facing text.

So the server's prose is used only for **which field**. Since Phase 6 the
envelope also carries `fieldIssues` - a code per problem (`TOO_LONG` with
its limit, `REQUIRED`, `INVALID_FORMAT`) - and the client turns that code
into the same sentence its own validator would have produced.
cùng file — phép dịch mã
function serverErrorFor(path: string, issue: FieldIssue | undefined): true | object {
  switch (issue?.code) {
    case 'REQUIRED':
      return { reason: 'required' };
    case 'TOO_LONG':
      return { reason: 'tooLong', max: issue.limit };
    case 'TOO_MANY':
      return { reason: 'tooManyTags', max: issue.limit };
    case 'INVALID_FORMAT':
      return { reason: FORMAT_REASONS[path] ?? 'invalid' };
    case 'INVALID_VALUE':
    case 'UNKNOWN_FIELD':
      return { reason: 'invalid' };
    default:
      return true;      // không có mã → câu chung "server từ chối giá trị này"
  }
}

const FORMAT_REASONS: Readonly<Record<string, string>> = {
  email: 'invalidEmail',
  phone: 'invalidPhone',
  dateOfBirth: 'invalidDate',
  'address.country': 'invalidCountry',
};

Kết quả cuối cùng rất đáng chú ý: một lỗi từ server hiện ra bằng đúng câu mà validator client sẽ hiện. Người dùng không phân biệt được — và không cần phân biệt. Với họ, "tên quá dài" là "tên quá dài", bất kể ai phát hiện.

Chú ý FORMAT_REASONS tra theo đường dẫn: INVALID_FORMAT trên email và trên address.country là hai câu khác nhau, vì một email sai và một mã quốc gia sai được giải thích khác nhau.

3.8 Xoá lỗi server khi người dùng sửa

customers/customer-form/validation-messages.ts
/**
 * Removes the server's verdict from a control.
 *
 * Called when the value changes: the server rejected the old value, and
 * leaving the error in place would keep a corrected field marked as wrong.
 */
export function clearServerError(control: AbstractControl): void {
  if (!control.errors || !(SERVER_ERROR in control.errors)) {
    return;
  }
  const rest: ValidationErrors = {};
  for (const [name, detail] of Object.entries(control.errors)) {
    if (name !== SERVER_ERROR) {
      rest[name] = detail;
    }
  }
  control.setErrors(Object.keys(rest).length ? rest : null);
}

Lỗi của validator client tự biến mất khi giá trị hợp lệ — chúng chạy lại mỗi lần gõ. Lỗi của server thì không: nó được gán vào bằng tay, nên phải được gỡ ra bằng tay. Thiếu hàm này, người dùng sửa email thành một địa chỉ hoàn toàn khác và ô vẫn đỏ.

Chú ý dòng cuối: setErrors(null) khi không còn lỗi nào khác — vì một object rỗng {} vẫn làm control INVALID.

5.1 Hai nguồn lỗi, một chỗ hiển thị

Mục 6Đánh đổi & phương án bị loại

Mã lý do thay vì câu chữ — ADR-0035

Phương án bị loại: hiển thị message của server. Bị loại vì nó phá hai quy tắc cùng lúc — không hiện lỗi thô, và không hiện chữ chưa dịch. Giá phải trả: server phải gửi thêm fieldIssues, và client phải có một bảng tra mã. Nhưng chú thích ghi rõ đây là trả một khoản nợ đã ghi sổ (debt row 12).

Async validator không chặn khi mạng hỏng

Phương án bị loại: coi lỗi mạng là "không hợp lệ". Bị loại vì khi đó người dùng không lưu được vì một lý do không liên quan gì tới dữ liệu họ nhập — và server vẫn sẽ kiểm lại. Giá phải trả: thỉnh thoảng người dùng bấm Lưu rồi mới nhận 409.

Một thông báo tại một thời điểm

Phương án bị loại: liệt kê mọi lỗi của một ô. Bị loại vì nói hai điều về một ô là người dùng không đọc điều nào. Giá phải trả: phải duy trì một thứ tự ưu tiên — và thứ tự đó là một quyết định thiết kế, không phải một danh sách ngẫu nhiên.

Regex cố ý dễ dãi

Cả email lẫn số điện thoại. Chú thích cho số điện thoại nói thẳng tiêu chí: "A strict national format would reject a legitimate international number, which is the more expensive mistake." Chọn sai hướng ở đây nghĩa là chặn khách hàng thật.

Mục 7Làm kiểu ngây thơ thì vỡ thế nào

1. Async validator không hoàn tất

Thiếu first() (hoặc take(1)) thì Observable không bao giờ complete, control kẹt PENDING, và nút Lưu không bao giờ bật. Không lỗi, không cảnh báo — chỉ là một form không gửi được.

2. Validator định dạng báo lỗi khi ô rỗng

Mọi ô tuỳ chọn để trống đều đỏ. Người dùng không điền số điện thoại và bị báo "số điện thoại không hợp lệ". Luôn return null cho giá trị rỗng — "bắt buộc" là validator khác.

3. setErrors đè mất lỗi client

control.setErrors({ server: true }) xoá sạch required và tooLong đang có. Ô trở thành "chỉ có lỗi server", và khi người dùng sửa, lỗi client không quay lại cho tới lần gõ kế tiếp. Luôn trải lỗi cũ vào.

4. Quên clearServerError

Người dùng đổi email thành một địa chỉ hoàn toàn mới và ô vẫn đỏ với thông báo cũ. Họ sửa đi sửa lại một thứ đã đúng. Lỗi client tự biến mất; lỗi gán tay thì phải gỡ tay.

5. Bỏ qua unmatched

Server báo lỗi ở một đường dẫn không khớp control nào — ví dụ khoá _ cho lỗi của cả payload. Nếu không xử lý, lỗi biến mất hoàn toàn: form không hiện gì, người dùng bấm Lưu lại, lại thất bại, và không ai nói vì sao.

6. Để validator client là lời cuối

Client không phải biên bảo mật. Mọi quy tắc phải được server kiểm lại — và nếu một quy tắc chỉ sống ở client (như phoneRequiredWhenActive ở đây), phải nói ra điều đó thay vì ngụ ý rằng server cũng kiểm.

Bài 1 — Quan sát async validator làm việc

~25 phút · không sửa code

  1. Mở /customers/new, DevTools → Network, lọc Fetch/XHR.
  2. Gõ chậm một email hợp lệ, từng ký tự, chờ giữa mỗi ký tự. Đếm request.
  3. Xoá hết, gõ thật nhanh cùng email đó. Đếm lại.
  4. Gõ khong-phai-email. Có request nào không? Vì sao?
  5. Bật "Offline" trong DevTools, gõ một email mới, rồi thử bấm Lưu. Form có chặn bạn không?
Bạn phải thấy gì

(2) nhiều request — mỗi lần dừng quá 400ms là một lượt. (3) một request — timer dẫn đầu, và Angular unsubscribe lượt trước mỗi lần giá trị đổi.

(4) không request nào: blockedBySyncErrors chặn trước khi tới timer.

(5) form không chặn. catchError(() => of(null)) coi "không biết" là "không có lỗi", và để server quyết định. Đây là quyết định thiết kế, không phải sơ suất.

Bài 2 — Phá ba thứ, mỗi thứ một bug

~40 phút · sửa rồi hoàn nguyên sau mỗi bước

Làm từng cái một, quan sát, rồi hoàn nguyên trước khi sang cái tiếp.

  1. Bỏ first() trong email-availability.validator.ts. Gõ một email rồi bấm Lưu.
  2. Bỏ if (!value) return null khỏi phoneFormat. Mở form mới và nhìn ô Phone.
  3. Đổi shouldShow thành control.invalid && (control.dirty || submitted). Bấm vào ô Full name rồi bấm ra, không gõ gì.
Ba triệu chứng
  1. Nút Lưu chuyển sang trạng thái bận và ở đó mãi mãi. Control kẹt PENDING, nên nhánh chờ trong submit() không bao giờ nhận được tín hiệu hoàn tất.
  2. Ô Phone đỏ ngay khi form vừa mở, với "số điện thoại không hợp lệ" — cho một ô tuỳ chọn mà người dùng chưa chạm vào. Thực tế bạn sẽ không thấy ngay vì shouldShow giấu nó, nhưng form đã INVALID và nút Lưu không bật. Hai lỗi lồng nhau.
  3. Không có lỗi nào hiện ra, dù ô bắt buộc đang trống. Người dùng không hiểu vì sao Lưu không ăn. dirty là sai công cụ ở đây.

Bài 3 — Hoà một lỗi server vào form

~45 phút · dùng fault injection

Mock API gây lỗi theo yêu cầu qua header x-mock-scenario (docs/mock-backend.md). Tìm kịch bản trả 422 và dùng nó.

  1. Dùng page.route trong một test Playwright tạm, hoặc DevTools để thêm header, rồi lưu một form.
  2. Quan sát: ô nào bị đánh dấu? Câu chữ là gì — tiếng Anh hay tiếng Việt?
  3. Sửa ô đó. Thông báo có biến mất ngay không?
  4. Bây giờ đọc serverErrorFor và xác định: nếu server gửi INVALID_FORMAT cho address.country, người dùng đọc được câu nào?
Điều bạn phải xác nhận

Câu chữ phải bằng ngôn ngữ đang chọn, và phải giống hệt câu mà validator client sẽ hiện cho cùng vấn đề. Nếu bạn thấy một chữ tiếng Anh nào do backend viết, đó là một bug — và là bug phá quy tắc 1 và 6 cùng lúc.

(3): phải biến mất ngay khi giá trị đổi, nhờ clearServerError. Nếu nó ở lại, hãy tìm xem ai quên gọi hàm đó.

(4): FORMAT_REASONS['address.country'] → 'invalidCountry' → khoá customers.validation.invalidCountry — cùng câu mà countryCode validator sẽ hiện.

Bài 4 — Viết một async validator cho một bài toán khác

~60 phút · branch learning/*

Viết customerCodeAvailableValidator: kiểm xem một mã khách hàng (C-000123) đã tồn tại chưa. Đủ bốn quyết định ở mục 3.4.

  • Debounce bên trong, không ở component.
  • Bỏ qua nếu validator sync đã báo sai định dạng.
  • Lỗi mạng không chặn form.
  • Hoàn tất — first().
  • Một spec: gõ nhanh → một request; lỗi mạng → null; định dạng sai → không gọi server.
Hai câu hỏi thiết kế bạn phải tự trả lời

1. Khi sửa, mã của chính bản ghi này có bị coi là trùng không? Không — và đó là lý do validator email nhận excludeId: () => CustomerId | null. Chú ý nó là một hàm: id chỉ biết sau khi bản ghi nạp xong, còn validator được gắn vào form sớm hơn. Truyền giá trị thì sẽ bắt được null mãi mãi.

2. Validator này có nên tồn tại không? Câu hỏi thật, và câu trả lời ở repo này là không: customerCode do server sinh ra, client không đặt được. Nếu bạn vẫn làm bài tập này, hãy ghi lại rằng bạn đang luyện cơ chế trên một tình huống giả — và ở dự án thật, câu hỏi "field này có do client đặt không" phải hỏi trước khi viết validator.

Mục 11Tự kiểm tra

1. Validator thuộc về control hay group — tiêu chí là gì?

"Một control đơn lẻ có trả lời được câu hỏi này không?" Không thì nó thuộc về group. Ô city không biết nó có bắt buộc hay không — điều đó phụ thuộc vào line1.

2. Vì sao validator định dạng phải trả null cho ô rỗng?

Vì "rỗng" là việc của required, không phải của validator định dạng. Thiếu nó thì mọi ô tuỳ chọn để trống đều bị đánh dấu sai, và form không bao giờ hợp lệ.

3. Ba thứ bắt buộc trong một async validator?

timer dẫn đầu (debounce, và huỷ miễn phí từ framework); catchError trả of(null) (mạng hỏng không chặn người dùng); và first() (phải hoàn tất, nếu không kẹt PENDING).

4. Vì sao không hiển thị message của server?

Vì đó là tiếng Anh do schema sinh ra, nhắc tên field nội bộ, và không dịch được — hiển thị nó phá cả quy tắc "không lỗi thô" lẫn "không chữ chưa dịch". Message chỉ dùng để biết field nào; lý do đến từ fieldIssues dưới dạng mã.

5. Vì sao applyServerFieldErrors phải markAsTouched?

Vì shouldShow yêu cầu touched hoặc submitted, và người dùng vừa bấm Lưu nên chờ họ blur là chờ một việc sẽ không xảy ra. Không có dòng này, lỗi được gán vào nhưng không hiện ra.

6. Vì sao cần clearServerError?

Vì lỗi của server được gán bằng tay nên không tự biến mất khi giá trị đổi — khác lỗi của validator client, vốn chạy lại sau mỗi phím gõ. Thiếu nó, một ô đã sửa đúng vẫn bị đánh dấu sai.

7. Chuyện gì xảy ra với một đường dẫn lỗi không khớp control nào?

Nó được trả về cho trang để hiện phía trên form — kể cả khoá _ mà envelope dùng cho lỗi của cả payload. Nếu nuốt nó, người dùng bấm Lưu thất bại mà không ai nói vì sao.
